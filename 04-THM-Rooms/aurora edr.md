## What is an EDR?

EDR stands for Endpoint Detection and Response.

Unlike traditional antivirus which only blocks known 
malware signatures, EDR takes a proactive approach:

| Feature | What it does |
|---------|-------------|
| Detection | Identifies suspicious behaviour in real time |
| Response | Takes automated or manual action on threats |
| Insights | Provides context around detected threats |
| Forensics | Records activity for post-incident investigation |
| Integration | Connects with SIEM and other security tools |

**Key difference from antivirus:**
Antivirus = blocks known bad files
EDR = monitors ALL behaviour and detects unknown threats

## What is ETW?

ETW stands for Event Tracing for Windows.

It is a Windows OS built-in mechanism that provides 
high-performance logging for applications, drivers, 
and the OS itself. It is the foundation that many 
security tools build on — including Aurora EDR and 
Windows Event Log itself.

### ETW Architecture — Three Components

**1. Providers**
Applications, drivers, or OS components that generate 
events. Every provider has a unique GUID identifier.

Examples:
- Microsoft-Windows-Kernel-Process (tracks processes)
- Microsoft-Windows-DNS-Client (tracks DNS queries)
- Microsoft-Antimalware-Engine (tracks AV detections)

**2. Controllers**
Start and stop ETW tracing sessions. They define which 
providers to collect from and configure the session 
parameters like buffer size and log file location.

**3. Consumers**
Applications that receive and process the events 
generated by providers.

Examples of consumers:
- Windows Event Log
- Aurora EDR
- Microsoft Defender
- Any SIEM agent

### ETW Data Flow
Provider (generates event)

↓

Controller (manages session)

↓

Consumer (receives and processes event)

↓

Security Tool (Aurora/SIEM/Defender)

**Why ETW matters for SOC:**
ETW gives security tools visibility into OS internals 
that would be impossible to get any other way. Process 
creation, network connections, file operations, registry 
changes — all flow through ETW.

## What is Aurora EDR?

Aurora is an Endpoint Detection and Response tool 
built by Nextron Systems. It uses:
- ETW for collecting Windows telemetry
- Sigma rules for detection logic
- Real-time alerting through Windows Event Log

**Key advantage:**
Aurora uses the same Sigma rules you write manually 
for SIEM detection — meaning the detection engineering 
skills from SigHunt room apply directly here.

## Aurora Detection Presets

Aurora has four performance/security presets:

| Preset | Security Level | Performance Impact |
|--------|---------------|-------------------|
| Intense | Maximum | Highest CPU/memory usage |
| Standard | High | Balanced — default recommendation |
| Reduced | Medium | Less security, better performance |
| Minimal | Low | Minimal security, lowest impact |

**In production SOC environments:**
Standard is the recommended default. It balances 
detection coverage with acceptable system performance.

Intense is used during active incident response when 
you need maximum visibility regardless of performance.

### Q1: Title of the first event rule

**How I found it:**
Filtered Event Viewer to show only Aurora Agent events.
Used the hint which suggested checking for Event ID 1 
(process creation events) first.

**Answer: Process Reconnaissance via WMIC**

**What this means:**
WMIC (Windows Management Instrumentation Command-line) 
is a legitimate Windows tool. Attackers use it to 
enumerate system information during reconnaissance:
wmic process list

wmic computersystem get username

wmic os get caption

Aurora detected this because a Sigma rule exists for 
suspicious WMIC enumeration activity.

**MITRE ATT&CK:** T1047 — Windows Management 
Instrumentation

---

### Q2: Rule ID of the matching Sigma rule

**How I found it:**
Same event as Q1. Aurora events include the full 
Sigma rule metadata — title, ID, level, and description 
are all visible in the event details panel.

**Lesson:**
Aurora embeds the complete Sigma rule information 
in every detection event. This means you can immediately 
see exactly which rule fired and why without having 
to cross-reference a separate rule database.

---

### Q3: Sigma rule level of the event

**How I found it:**
Same event as Q1 and Q2. The level field is visible 
in the event details alongside the rule ID.

**Sigma levels reference:**
- informational — low priority, for awareness
- low — minor suspicious activity
- medium — moderately suspicious
- high — likely malicious, investigate promptly
- critical — confirmed malicious, respond immediately

### Q4: Rule title of the second event

**This was the trickiest question.**

**Why it was tricky:**
When the .bat file ran, it automatically created a 
file called password.txt on the Desktop. Aurora 
detected this as a suspicious file creation event 
(Event ID 11).

The problem: this event only appears ONCE in Event 
Viewer. If you close Event Viewer and reopen it, 
the event is gone from the live view.

**How I found it:**
Kept Event Viewer open the entire time after running 
the .bat file. Scrolled through events while still 
in the same session and found the file creation event.

**Key lesson:**
When running malware simulations, open your monitoring 
tool BEFORE executing the sample. Never close and 
reopen during the investigation or you may miss 
transient events.

**Event ID used:** 11 (File Creation)

This confirms that Aurora monitors file system activity 
through ETW in addition to process creation.

Both found within the same Event ID 11 detection 
event as Q4. Aurora includes full rule metadata 
in every event so all remaining answers were visible

## Aurora Event Structure

When Aurora detects something, the Windows Event 
Log entry contains:
Event ID: [Aurora event ID]

Source: Aurora Agent
Event Details:

Rule Title: [Sigma rule name]
Rule ID: [Unique rule GUID]
Rule Level: [informational/low/medium/high/critical]
Description: [What was detected]
Process: [What triggered it]
Command Line: [Exact command used]
User: [Who ran it]
Timestamp: [When it happened]


This structured format means every Aurora alert 
contains the full context needed for investigation 
without needing to look anything up separately.

## Key Takeaways

**ETW is the foundation of Windows security visibility:**
Without ETW, security tools would be blind to most 
OS-level activity. Understanding ETW helps you 
understand WHY your EDR sees what it sees.

**Aurora bridges Sigma and EDR:**
If you can write Sigma rules you can extend Aurora's 
detection capability. Adding custom rules for your 
specific environment is a real SOC skill.

**Event ID 1 vs Event ID 11:**
- Event ID 1 = Process created (what ran)
- Event ID 11 = File created (what was written to disk)
Different attack techniques leave different event types.
Always check which EventID is relevant before filtering.

**Timing matters in live investigations:**
Some events are transient — they appear once and 
disappear. In real incidents this means your monitoring 
must be running BEFORE the attack happens. This is 
why continuous monitoring is essential, not reactive.

## ETW vs Windows Event Log

| Feature | ETW | Windows Event Log |
|---------|-----|-----------------|
| Performance | Very high | Moderate |
| Detail level | Extremely detailed | Standard |
| Real-time | Yes | Yes |
| Persistence | Session-based | Persistent on disk |
| Used by | Security tools, profilers | Admins, SIEM |

ETW is the raw firehose of Windows activity.
Windows Event Log is a structured subset of that.
Aurora taps directly into ETW for maximum visibility.
