# Aurora EDR and Endpoint Detection

This document outlines the features and implementation of **Aurora EDR** (Endpoint Detection and Response), developed by Nextron Systems. It covers EDR concepts, real-time Sigma rule evaluation on endpoints, Event Tracing for Windows (ETW), and how to analyze Aurora alerts.

---

## Part 1: What is Aurora EDR?

Aurora is a lightweight Endpoint Detection and Response (EDR) agent. While traditional EDR agents are often heavy and rely on cloud-based machine learning models, Aurora operates locally on the endpoint and evaluates system events in real-time using **Sigma rules**.

It runs as a Windows service and writes alerts directly to the Windows Event Log. This makes it highly compatible with existing log forwarders (like Wazuh or Splunk), which can immediately collect Aurora's high-fidelity alerts and forward them to the SIEM.

---

## Part 2: How Aurora EDR Works

Aurora intercepts system activity by tapping into low-level Windows monitoring mechanisms:

```text
  Windows Kernel (ETW / API Calls)
                 │
                 ▼
       [ Aurora EDR Agent ] ◄─── (Evaluates local Sigma Rules)
                 │
                 ▼
    Windows Event Log (Aurora)
                 │
                 ▼
       SIEM / SOC Dashboard
```

### 1. Event Tracing for Windows (ETW)
Aurora uses ETW to monitor system events. ETW is a kernel-level tracing facility that logs events generated by both user-mode applications and kernel-mode drivers. This allows Aurora to monitor:
*   Process injection attempts (e.g., shellcode injected into `explorer.exe`).
*   Direct access to the Local Security Authority Subsystem Service (LSASS) memory.
*   Suspicious loading of raw drivers or DLLs.

### 2. Sigma Rules Evaluation
**Sigma** is a generic, open signature format used to describe log events (similar to how Snort is for network traffic and YARA is for files). 
Instead of sending raw logs to a central SIEM for Sigma evaluation, **Aurora evaluates Sigma rules locally on the endpoint**. If a process command line matches a local Sigma rule, Aurora flags it instantly.

---

## Part 3: Aurora Configuration and Alert Channels

Aurora's alerts are logged directly to a dedicated Windows Event Log channel:
`Applications and Services Logs / Aurora / Operational`

### Critical Aurora Event IDs
*   **Event ID 1:** Information (general audit logs).
*   **Event ID 2:** Warning (suspicious activity detected, low-severity Sigma match).
*   **Event ID 3:** Alert (high-severity threat detected, high-fidelity Sigma match).
*   **Event ID 4:** Critical (known malicious attack pattern detected, immediate action required).

## Part 4: Analytical Case Study: Detecting LSASS Access

A primary objective of an attacker post-compromise is to dump credentials from the LSASS memory space (using tools like Mimikatz or Task Manager).

### 1. The Threat
An attacker executes a script to dump the memory of `lsass.exe`.

### 2. Aurora Detection (ETW + Sigma)
Aurora's ETW monitors detect an unauthorized process opening a handle to `lsass.exe` with access mask `0x1F0FFF` (full access) or `0x1010` (query and read). 
Aurora evaluates this handle request against the local Sigma rule `win_susp_lsass_access.yml` and triggers an **Event ID 4 (Critical Alert)**.

### 3. Log Output Example
```text
Log Name:      Aurora/Operational
Source:        Aurora
Event ID:      4
Level:         Critical
Description:   Sigma Rule Match: LSASS Memory Dump / Access Detected
               Rule Name: Suspicious LSASS Access
               Process: C:\Windows\System32\cmd.exe
               Target: C:\Windows\System32\lsass.exe
               Mitre ID: T1003.001
```

By placing Aurora on the endpoint, defenders detect credential dumping immediately at the source, preventing lateral movement before the attacker can use the stolen hashes.
